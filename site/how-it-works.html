How it works

Checking a machine that may be lying.

A machine worth checking may already belong to someone else, and whoever has root on it can change any file, program or database on it. telltale is built around that.

Two halves: collection and judging

Collection runs on the machine and reads everything telltale needs into one record. Judging compares that record with the snapshot, with the distribution's signed packages, with the checklist and with the suspicious-on-any-machine rules, and ranks what it finds.

When you carry telltale to a machine, both halves run there. In server mode only collection runs on the machine: the server copies the collector over, reads the record back over SSH and does all the judging itself. The machine needs no internet access, and the judging and the package cache stay on the trusted side.

The machine may lie

  • It brings its own code. telltale is one static binary that loads none of the machine's libraries, so a replaced libc or an /etc/ld.so.preload entry cannot hook it. It uses Go's own DNS resolver and TLS.
  • It reads the kernel's and the filesystem's view directly. Processes come from /proc, sockets from /proc/net, files from the filesystem and packages from /var/lib/dpkg/status. It does not ask the machine's programs.
  • It compares with the machine's own tools. It runs ps, ss, ls and lsmod from the system directories with a clean environment and compares what they print with what it reads itself. Something telltale sees and a tool hides is tampering: it is what a userland rootkit does.
  • The snapshot never lives on the machine. You keep it somewhere else, encrypted with a passphrase, or the server keeps it, encrypted at rest. It is never written to the machine's disk.
  • Keys are built in. The Debian and Ubuntu archive keys are built into telltale. The machine's current keyrings and its package database's checksums are never proof of anything; the one exception is scan --offline, which says so at the top of the report.
  • The machine's clock is not trusted either. Signature dates are checked against the newest date the archive itself signed.
  • No secrets are kept. Password hashes become a keyed digest, private key files are recorded by hash, permissions and owner only, and secrets in startup files are replaced by keyed digests before anything is stored or reported.

Package verification

For each installed package, telltale wants to know whether the files on disk are the ones the distribution shipped.

  1. It reads the installed packages and versions from /var/lib/dpkg/status.
  2. It fetches the distribution's signed index from the official archive, checks the signature with the keys built into telltale, and follows the chain of hashes to each package.
  3. It downloads each package it needs, checks its hash, unpacks it, and compares every file with the one on disk: its content, and the mode bits that grant privilege.
  4. A version the archive no longer has comes from snapshot.debian.org or Ubuntu's snapshot service, which keep signed indexes.

Without a snapshot it verifies the package files in security-relevant places (programs, libraries, PAM and kernel modules, /boot) and the packages' maintainer scripts; with a snapshot, the package files that changed since. A mismatch is tampering. A file that cannot be verified (the version is in no trusted source, its repository has no key telltale trusts, the archive could not be reached) goes into one note, except setuid programs, kernel and PAM modules and boot files, which are each a backdoor sign.

A machine that is cut off the network is checked with a reference bundle: collect on the machine, build the bundle on one that has a connection, and carry it back. Everything in the bundle is checked again against the built-in keys when it is used.

The regression rule

Attackers loosen settings to keep their way back in: they turn root login over SSH back on, add a sudo rule without a password, switch the firewall off. So a checklist item that passed in the snapshot and fails now is reported as tampering, not as a weak setting. The same holds for an item you accepted as an exception, if its value changes from the one you accepted. Items that were already failing when the snapshot was taken stay weak settings.

Which changes count as routine

Without a rule for routine changes, every package update would bury the real findings, and a report people learn to ignore has failed.

  • An upgrade to a newer version from a trusted source is explained. Its changed files go into one quiet "explained" group, and only when their new hashes match the new signed package.
  • A version nothing trusted confirms explains nothing. Typing a new version into dpkg/status does not make a replaced file look like an update.
  • A newly installed package is a note, and a backdoor sign when it adds something that runs with special rights or reaches the network.
  • A downgrade is a backdoor sign: going back to an old, vulnerable version is a known way back in.
  • Everything else that changed is unexplained, and ranked by where it is: a change to cron, systemd, SSH, sudo, PAM, shell start-up files or ld.so.preload ranks higher than a change to a data file.

Reading a report

The report starts with the machine, what it was compared against and what it could not rule out. Then the findings, most serious first, each with its evidence, why it matters and the command that would fix it. The reports page has real ones.

Tampering

A checklist item that held in the snapshot and fails now, a system file that does not match its signed package, or something the machine's own tools hide.

Backdoor sign

A new root SSH key, a second account with user id 0, a cron job or systemd unit that calls out, an unknown PAM module, a setuid program no package ships.

Weak setting

A checklist item that is not met (and, with a snapshot, was not met then either).

Note

Worth a look, not a sign of trouble on its own.

After the findings come the explained changes, the exceptions in force and the checks it had to skip. The exit code says what it found: 0 nothing, 1 notes or weak settings only, 2 tampering or a backdoor sign, 3 the scan could not run.

Exceptions

Some findings are intended: a checklist item you leave failing on purpose, a module you built yourself. You can accept a finding as an exception (in the web UI, or telltale accept when you carry it). The exception records the exact value it accepted, and the finding comes back as soon as the value changes. Every report lists the exceptions in force. The clean machine on the reports page has some.

What no check on the machine can rule out

A kernel-level rootkit can hide anything from anything that runs on top of the kernel, telltale included. Every report says so. Checking the disk from another, trusted machine is the only answer, and it is planned for a later version.

The full details are in the repository: docs/how-it-works.md, and every check in docs/checks.md.
